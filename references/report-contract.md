# 步伐报告契约

## 核心原则

报告不是工作流水账，而是有证据的诊断型复盘：从当天工作和 AI 对话中识别可迁移的局限，说明它如何限制当时的推理与提问，再用可学习、可实践、可验证的材料精准补给。

标题必须是：

```markdown
# YYYY-MM-DD 步伐
```

## 章节结构与篇幅

### 固定核心章节

- `做了什么`：约占全文 10%–15%，只作为诊断所需的成果索引。
- `暴露的问题、盲区与困难`：约占全文 40%–50%，承担主要分析。
- `定向补给`：约占全文 30%–40%，逐项回应前述问题。

### 条件章节

- `昨日概览`：一句话能显著帮助理解当天主线时才出现，最多三句话。
- `学到了什么`：存在明确学习证据且不能自然并入问题分析时才出现。
- `数据缺口`：缺口会实质影响诊断可信度时才出现，只写影响结论的缺口。

章节出现时按以下顺序排列：`昨日概览`、`做了什么`、`学到了什么`、`暴露的问题、盲区与困难`、`定向补给`、`数据缺口`。目标长度为 2500–4000 个中文字符，作为可读性目标而不是配额；证据不足时生成更短的透明报告，不得填充或虚构。

## 章节要求

### 昨日概览（条件章节）

最多三句话概括当天主线，不复述任务清单，不写常规来源统计。只有主线概括能帮助读者理解后续诊断时才保留。

### 做了什么

按**业务主题**合并任务，不按聊天顺序、工具调用或实现步骤拆条。每项只包含：

- **状态：** 完成、部分完成或受阻。
- **目标与结果：** 一句话说明目标，一句话说明可验证结果或未完成点。

主句使用“完成、实现、修复、重构、优化、配置、梳理、确定、输出”等**成果动词**。只有最终答复与测试、验证、文件动作或可核对结果共同支持时，才算**完成证据**；仅有用户请求时写“待验证”，仅有部分动作时写“部分完成”。只有同一问题反复失败、明确卡住、等待外部依赖或关键决策未定，且复盘结束时仍未解决，才算**真正受阻**。

同一交付链路只保留一个结果项。过程信息、排障轮次、命令尝试和实现细节不展开；只有某个过程事实支撑后文诊断时，才在问题项的“观察事实”中出现。

### 学到了什么（条件章节）

只有对话中存在明确学习证据，而且该内容不能自然并入问题诊断时才写。用“提问 → 获得的知识 → 可迁移应用”表达；推测性的收获标明“待验证”。

### 暴露的问题、盲区与困难

选择 2–4 个高价值问题，不追求数量。每项按以下顺序完整书写：

- **观察事实：** 对话、动作、验证结果或反复困难中可核对的证据。
- **当时的理解或默认假设：** 从提问顺序和采取的动作中得到的有限解释；证据不足时明确标记待验证。
- **局限类型：** 从“看待和理解问题的视角局限”“工作流与方法局限”“认知模型或知识缺口”中选择一个主类型，必要时补充次类型。
- **如何限制推理与提问：** 明确指出哪些可能性没有被考虑、哪些证据没有先索取、问题被怎样过早收窄或错误表述。
- **造成的影响：** 对效率、质量、判断或后续行动的具体影响。
- **反证与待验证：** 写出可能推翻当前解释的事实，以及日志尚不能确认的部分。
- **下一步验证动作：** 一个能在后续相似工作中验证或纠正该判断的小实验。

问题选择按以下优先级：

1. 能暴露可迁移思维模式的问题，高于一次性的工具错误。
2. 有完整逻辑链和多项证据的问题，高于看似深刻但缺少证据的问题。
3. 能通过学习或实践改善的问题，高于无法行动的泛化描述。

不得进行心理、人格、动机或固定能力诊断，不得把一次提问泛化为长期特征。若只能确认工具错误，不能据此虚构认知盲区；应保守写成工作流问题或放弃该项。

### 定向补给

总计推荐 1–3 项最高价值材料，不按问题数量机械凑数。每项固定包含：

- **对应问题：** 指向“暴露的问题、盲区与困难”中的问题编号。
- **材料：** 类型、可点击标题和本次运行中核验过的链接。
- **匹配理由：** 它针对的具体局限，以及为什么比其他材料更匹配。
- **主要学习内容：** 材料覆盖的主题、方法、章节或练习。
- **主要知识：** 学习后应形成的概念、判断框架或操作方法。
- **实践产出：** 把学习转化为清单、模板、决策记录、实验、代码练习或其他可检查成果。
- **验证标准：** 下次遇到相似问题时，如何判断推理、提问或工作流已经改善。
- **投入：** 预计阅读或试用时间。

一个材料可以服务多个高度相关的问题，但必须分别说明对应关系。技术事实优先使用官方文档、原始论文或项目仓库；当天问题涉及书籍、思维、决策、习惯或生活主题时，可推荐书籍的具体章节、文章或实践材料，不得默认只推荐技术资料。对 skill/plugin，可验证时标明已安装、可安装或可用性待验证；只推荐，不执行安装。链接必须在本次运行中核验，不得凭记忆虚构。

### 数据缺口（条件章节）

常规来源覆盖、去重数和截断数保留在内部分析中，不自动进入报告。只有某个缺口会改变问题判断、证据强度或完成状态时才写本节，并说明：缺失了什么类型的证据、影响了哪条结论、因此采取了何种保守表述。

Codex 本地会话（CLI/VS Code）和 Claude Code 本地会话仍是提取时必须检查的基线。Codex 应用聊天是可选增强：默认环境没有相应工具时静默跳过，不构成数据缺口。只有实际尝试采集且结果影响结论时，才披露相关读取失败、列表窗口截断或范围不完整；除非可验证对应范围，不得使用无条件的“Codex 完整覆盖”。不得暴露绝对路径、文件名、消息正文或私有项目标识。

## 证据与隐私

- 使用“观察事实 / 有限解释 / 待验证”区分证据强度。
- 搜索查询只能来自 `search_brief` 或不超过 240 字符的等价脱敏摘要。
- 发布前扫描 Windows/Unix 绝对路径、用户名、仓库名、代码、密钥、token、密码和带凭据或敏感查询参数的 URL。
- 原始日志和局部回读内容只在本机处理，不进入联网查询。

## 发布门槛

仅当标题日期、三个固定核心章节、条件章节适用性、长度策略、链接和隐私检查全部通过后，才把临时草稿用原子替换发布到 `D:\Web\new_think\YYYY-MM-DD步伐.md`。任何检查失败都不得改动已有同日报告；全部通过后允许原子刷新并替换已有同日报告。

Notion 是独立的可选发布阶段。它只能在本地原子刷新成功且用户明确要求发布时执行；Notion 失败不得影响已经验证的本地报告。
